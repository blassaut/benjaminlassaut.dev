# E2E mutation testing: from ticket to planted bug

A method and a small tool to answer one question about an end-to-end or API
test suite: **if this bug came back, would a test notice?**

We plant bugs on purpose, outside the application code, then run the suite.
A planted bug that leaves every test green is proof that the suite does not
check that behaviour, whatever the coverage or scenario count says. This is
the guard-rail we want against tests that merely "walk through" the product,
a common shape for tests written quickly or generated by an AI.

The method needs no access to the application source. It works on anything
a browser or an HTTP client can reach.

## 1. The method in one page

**Vocabulary.**

| Term | Meaning |
|---|---|
| Mutant | One bug we plant on purpose, described as data in a YAML file. Always tied to a ticket. |
| Catalog | The set of YAML files in `e2e/mutation/mutants/`. One file per user flow. |
| Scope | The test files (and optional tags) a mutant is run against. |
| Killed | At least one test in scope failed with the mutant planted. The suite would catch this bug. |
| Survived | Every test in scope passed with the mutant planted. The suite would miss this bug. |
| Not applied | Every test passed, but the mutant never changed anything. The mutant is broken, not the tests. |

**The loop.**

```
   ticket (incident or feature)
        │
        ▼
   write one mutant in the catalog          ← 5 minutes, YAML, no code
        │
        ▼
   node e2e/mutation/run.ts --only <id>     ← baseline, then mutant (stops at the first failing test)
        │
        ├── killed      → done. The mutant stays in the catalog as a permanent guard.
        ├── survived    → add the missing assertion to the test, re-run.
        └── not applied → fix the mutant (selector, url, scope), re-run.
```

**Where the mutants come from.** Two sources, both already in your ticketing
tool:

- **Incidents.** Every bug that reached production becomes a mutant during the
  post-incident review. This is the highest-value source: these are bugs that
  provably happen.
- **Feature tickets.** Each acceptance criterion, negated, is a candidate
  mutant. "The total includes VAT" gives "the total is shown without VAT".

**Who does what.**

| When | Who | What |
|---|---|---|
| Post-incident review | QA | Adds one mutant for the incident, runs it, opens a test task if it survives. |
| Refinement of a feature ticket | QA | Lists the mutants that the feature's tests must kill. |
| Pull request that adds or changes E2E tests | Author | Runs the mutants in scope. See [the merge rule](#5-the-merge-rule). |
| Pull request that touches `e2e/` | CI | Runs the mutants in scope (the whole catalog when shared E2E code changed). A mutant that was killed and is now survived means an assertion was lost. |
| After a UI refactor | Anyone | Runs the whole catalog on demand (Actions > Run workflow) to catch mutants that no longer apply. |

**What it costs.** Writing a mutant takes minutes. Running one takes as long as
the scenarios in its scope. Ten mutants on a flow of six scenarios is a few
minutes, because a mutant never runs against the whole suite.

## 2. Quick start

```bash
npm run test:mutation:e2e -- --list                 # what is in the catalog
npm run test:mutation:e2e -- --only <mutant-id>     # one mutant
npm run test:mutation:e2e                           # whole catalog, exits 1 if any is not killed
open reports/mutation-e2e/report.md                 # the report
```

Useful options:

| Option | Effect |
|---|---|
| `--only a,b` | Run only these mutant ids. |
| `--project desktop-chrome` | One browser only. Faster on a laptop. |
| `--changed-since origin/main` | Only mutants the E2E changes since that ref can affect: a changed test file selects the mutants scoped to it, a changed catalog file selects the mutants it defines, `.md` files are ignored, and any other E2E change (steps, fixtures, runner) selects every mutant. What CI does on pull requests. |
| `--workers 4` | Playwright workers per run (default `50%` of the CPUs, from `config.ts`). Lower it on a laptop. |
| `--stability 3` | Run the baseline three times. Use when you suspect flakiness. |
| `--no-fail` | Exit 0 whatever the result. For informational runs. |

The suite itself is untouched: `npm run test:e2e` behaves exactly as before.
A mutant is only planted when the `MUTANT` environment variable is set, which
the runner does for you:

```bash
MUTANT=legal-link-missing-from-footer npx playwright test visitor-reads-legal-notice
```

## 3. From a ticket to a mutant

### Worked example: an incident

Ticket **PORT-101**, from the incident tracker:

> *Title:* Legal Notice link missing from footer after redesign
> *Impact:* The legal page was unreachable for two days.
> *Root cause:* Footer links list rebuilt without the legal entry.

Steps:

1. **Name the flow.** The legal notice. The scenarios live in
   `e2e/features/visitor-reads-legal-notice.feature`, so the catalog file is
   `mutants/legal-notice.yaml`.
2. **State the concern in one sentence**, as a user would see it. Not the root
   cause, the symptom: *The "Legal Notice" link disappears from the footer.*
3. **Say what a good test would do.** One sentence starting with "fail when":
   *fail when the footer has no link to /legal.* This is the acceptance
   criterion for whoever fixes the test later.
4. **Pick the injection.** Look at the [operations table](#operations) and
   choose the one that reproduces the symptom. Here: remove the link.
5. **Write the entry:**

```yaml
- id: legal-link-missing-from-footer
  ticket: PORT-101
  concern: The "Legal Notice" link disappears from the footer
  expect: fail when the footer has no link to /legal
  scope:
    files: [visitor-reads-legal-notice]
  dom:
    - remove: '[data-testid="footer-link-legal"]'
```

6. **Run it:** `npm run test:mutation:e2e -- --only legal-link-missing-from-footer`.
7. **Act on the status.** Killed: commit the mutant, close the loop on the
   ticket. Survived: open a task "add assertion: footer links to /legal",
   commit the mutant anyway so CI keeps flagging it on every pull request in its scope.

### Worked example: a feature ticket

Ticket **PORT-140**, a feature:

> *Story:* As a visitor I can switch to dark mode and my choice is remembered.
> *Acceptance criteria:*
> 1. A toggle switches between light and dark.
> 2. The choice survives a page reload.

Negate each criterion that a real bug could break:

| Criterion | Mutant concern | Injection |
|---|---|---|
| The choice survives a reload | The chosen theme is forgotten on reload | `script: Storage.prototype.setItem = function () {}` |
| Saved theme applied before first paint | The bootstrap script in the HTML is broken | `response` replacing the script's condition with `false` |

Both are in `mutants/theme.yaml`. Writing them during refinement gives the
person who writes the tests a precise target: the tests are done when these
mutants are killed.

### Choosing a good mutant

- **One symptom per mutant.** A mutant that breaks three things is killed by
  the first test that notices any of them, and tells you nothing about the
  other two.
- **Prefer what a user would see.** A wrong amount, a missing link, a disabled
  button, a wrong status code. Avoid purely internal changes.
- **Prefer `response` over `dom` when the product has an API.** A rewritten
  response is exactly what a backend regression looks like. A DOM edit is an
  approximation, reserved for static sites and pure front-end concerns.
- **Do not make it crash everything.** A mutant that blanks the page is killed
  by every test, for the wrong reason. Keep the page usable, break one thing.
- **Do not write mutants for what no test could ever check.** Animation
  timings, colours, layout pixels. Those belong to visual or manual review.

## 4. Reading the report

`reports/mutation-e2e/report.md` has one line per mutant, then an
"Action required" section for anything not killed. `report.json` holds the
same data for scripts. In CI the Markdown is also shown in the job summary.

| Status | What it means | What to do |
|---|---|---|
| ✅ killed | A test in scope failed with the mutant planted. | Nothing. The mutant is now a permanent regression guard. |
| 🟥 survived | Every test in scope passed with the bug planted. | Add the assertion described in the mutant's `expect`, re-run with `--only`. |
| ⚠️ not-applied | Tests passed, but the mutant changed nothing on any page. | The selector or url matches nothing, or the scenarios never reach that element. Fix the mutant, not the tests. |
| ⚠️ no-tests | The scope matches no scenario. | Fix `scope.files` or `scope.tags`. |
| ⛔ baseline-failed | The scenarios fail without any mutant. | Fix the suite first. A red baseline makes every result meaningless. |
| 💥 error | Playwright did not produce a report. | Read the details in the report. |

Timing: a kill by timeout (a click on an element that no longer exists) takes
as long as the Playwright test timeout. It still counts as killed.

## 5. The merge rule

> A pull request that adds or changes end-to-end tests must show, in its
> description, which mutants those tests kill. A test that kills no mutant in
> its scope is not a test yet.

In practice:

1. Run `npm run test:mutation:e2e -- --changed-since origin/main` before
   opening the PR. CI runs the same command.
2. If the flow has no mutant yet, add at least one from the feature ticket
   (see [section 3](#3-from-a-ticket-to-a-mutant)) and make the new test kill it.
3. Never lower the bar by deleting or weakening a mutant to make a run pass.
   A mutant is removed only when the behaviour it guards is removed from the
   product, with the ticket that removed it.

Why pull requests that touch `e2e/` run the catalog: a mutant that was killed
for months and suddenly survives means an assertion was deleted or weakened.
That is the exact regression this method exists to catch, and it is
invisible in a green pipeline. Tests only change through `e2e/`, so there is
no need for a scheduled run on unchanged code.

## 6. Catalog reference

Files: `e2e/mutation/mutants/*.yaml`, one per user flow. Each file is a
top-level `mutants:` list. Every field below is validated on load; a broken
entry fails with a message naming the file, the index and the field.

### Mutant fields

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique, kebab-case. Used on the command line and in reports. Name the symptom: `contact-submit-disabled`. |
| `ticket` | yes | The incident or feature ticket this bug comes from. Jira, Linear, GitHub: any reference your team resolves. |
| `concern` | yes | One sentence, the symptom as a user sees it. |
| `expect` | yes | One sentence starting with "fail when": what a good test does. It is printed in the report when the mutant survives. |
| `scope.files` | yes | Test file names without extension. In this project, feature files: `visitor-reads-legal-notice`. Passed to Playwright as a file filter. |
| `scope.tags` | no | Tags to grep, e.g. `['@mobile']`. Combined with OR. |
| `dom` | one of | A list of page operations. See below. |
| `response` | one of | A network rewrite. See below. |

### Operations

DOM operations edit the rendered page. They are re-applied after every DOM
change, so a re-render cannot undo them. Selectors are standard CSS.

| Operation | Shape | Reproduces |
|---|---|---|
| `remove` | `remove: '<selector>'` | An element is missing. |
| `keepOnlyFirst` | `keepOnlyFirst: '<selector>'` | A list silently lost all items but the first. |
| `disable` | `disable: '<selector>'` | A control is disabled. |
| `setText` | `setText: { selector, text }` | A value or label is wrong. |
| `replaceText` | `replaceText: { selector, from, to }` | A word is wrong somewhere under the selector, even split across elements. |
| `setAttribute` | `setAttribute: { selector, name, value }` | A link points elsewhere, a target or aria attribute is wrong. |
| `script` | `script: \| <JavaScript>` | Anything else. Runs once before any page script. Escape hatch: prefer the operations above, they are checked for effect. |

A `dom` list may hold several operations; they all apply.

### Response rewrite

`response` intercepts every request whose URL matches `url` (a glob, same as
Playwright's `page.route`), fetches the real response, rewrites it, and hands
the result to the page.

| Field | Meaning |
|---|---|
| `url` | Glob such as `**/api/orders` or `**/*`. |
| `resourceTypes` | Optional filter: `[document]`, `[fetch, xhr]`. Without it, every matching request is rewritten. |
| `status` | Replace the HTTP status: `500`, `404`. |
| `replaceText` | List of `{ from, to }` applied to the body as text. |
| `json` | List of edits on the parsed JSON body: `{ path: 'data.items.0.price', set: 0 }` or `{ path: 'data.total', delete: true }`. |

Example for an API-backed product:

```yaml
- id: order-total-off-by-one-cent
  ticket: INC-4312
  concern: The order total shown differs from the total charged
  expect: fail when the displayed total is not the amount returned by the API
  scope:
    files: [checkout]
  response:
    url: '**/api/orders/*'
    resourceTypes: [fetch, xhr]
    json:
      - path: total
        set: 42.01
```

## 7. How the tool works

A handful of files, no framework:

| File | Role |
|---|---|
| `config.ts` | The only project-specific settings: where test files live, the command to run before Playwright, how Playwright is launched, workers per run, the report directory. |
| `catalog.ts` | Loads and validates the YAML files. Every rule in section 6 lives here. |
| `inject.ts` | Applies one mutant to a Playwright page: an init script for `dom`, a `page.route` for `response`. Counts effective changes. |
| `run.ts` | The command line and main loop: runs the baseline once per scope and each mutant once. |
| `select.ts` | Which mutants a run covers (`--only`, `--changed-since`). |
| `playwright.ts` | Builds the Playwright arguments, runs it, parses its JSON report and classifies the result. |
| `report.ts` | Console output and `report.{json,md}`. |

`select.ts`, `playwright.ts` and `report.ts` are unit-tested (`*.test.ts` next to them, run by `npm test`).

Plus `e2e/fixtures.ts`, the shared Playwright `test` object. It carries one
automatic fixture: when `MUTANT` is set, it plants the mutant on the page
before the scenario starts and, after it ends, annotates the test with
`mutant-not-applied` if nothing was changed. The runner reads that
annotation from Playwright's JSON report.

"Changed" is measured, not declared. A `remove` counts only if an element
was found and removed; a `replaceText` only if the text was present; a
`response` rewrite only if the body or status actually differs. This is what
makes "not applied" trustworthy, and it is the reason to prefer the
declarative operations over `script`.

## 8. Port it to your project

The method is independent of this repository. The tool assumes Playwright;
the same design works with Cypress by replacing `page.route` with
`cy.intercept` and the init script with `cy.on('window:before:load')`.

Checklist:

1. Copy `e2e/mutation/` into your test directory and add `yaml` to your dev
   dependencies.
2. Edit `config.ts`: point `testFilesDir` and `testFileExtension` to your
   test files (`tests`, `.spec.ts` for plain Playwright), set
   `prepareCommand` to whatever must run before Playwright (empty if
   nothing), keep `playwrightCommand` (program + arguments, run without a
   shell) unless you wrap it.
3. Create a shared `test` object, or extend the one you already have, with
   the automatic fixture from `e2e/fixtures.ts`. Make every spec or step
   file use it. For playwright-bdd, also list the fixtures file in the
   `steps` option of `defineBddConfig`.
4. Delete the sample catalog files and write your first mutant from your
   latest production incident.
5. Add `npm run test:mutation:e2e` to your scripts, and the workflow in
   `.github/workflows/mutation-e2e.yml` (or its equivalent) to run
   `--changed-since` on pull requests that touch E2E code, and the whole
   catalog on demand.
6. Write the merge rule from section 5 where your team reads its rules:
   contributing guide, PR template, `AGENTS.md` for AI assistants.

Node 22.18 or newer runs `run.ts` directly. For older versions, run it with
`npx tsx e2e/mutation/run.ts`.

## 9. Working with an AI

The method exists because AI-written tests tend to pass whatever the product
does. The same AI can help, with three rules.

- **Generate mutants from tickets, not from tests.** Give the model the
  incident or the feature ticket and the operations table, ask for catalog
  entries. Do not give it the test files at that stage: the point is to find
  what the tests miss, not what they already check.
- **Every generated mutant goes through the same qualification** as a human
  one: the run must say killed or survived, never not-applied. A mutant the
  model describes but that changes nothing on the page is worth nothing.
- **When a mutant survives and the AI writes the missing assertion**, ask for
  an assertion about the behaviour, not about the mutant. "The footer links
  to /legal" is right. "The element with this test id exists" is a test that
  will pass again the day the mutant is rewritten. A good check: the same
  assertion should kill several variants of the bug (link removed, link
  pointing elsewhere, link text changed).

Read the catalog entries an AI produces the way you read a test case: in
seconds, for plausibility. The tool checks the rest.

## 10. Limits

- **The catalog is the ceiling.** The method finds only the bugs someone
  thought of. Feed it with real incidents and it stays honest; leave it
  static and it becomes a checklist.
- **The current product is the oracle.** A mutant is judged against today's
  behaviour, assumed correct. A bug already in production is invisible to
  this method.
- **DOM mutants are approximations.** A removed element is not how bugs
  usually appear. Prefer `response` mutants on any product with an API.
- **Counting is not scoring.** Do not turn "17 killed out of 17" into a KPI.
  The number depends on which mutants were written. What matters is the
  list of survivors and how fast they are killed.
- **Flaky suites break the signal.** A test that fails randomly kills every
  mutant randomly. The baseline check catches the obvious cases; use
  `--stability 3` on suspicious flows.
